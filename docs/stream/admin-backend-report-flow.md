# Yuruicamp Admin 後端結訓報告流程

這份文件用於 15 分鐘結訓報告的口頭排練。報告不設獨立開場與結尾，直接從整體後端架構開始，依業務資料流介紹十個 Admin 功能。

---

## 1. 整體後端架構

**本段目的**

先建立共用技術地圖，讓後續功能可以直接說明各自的業務規則，不必反覆介紹系統分層。

**核心提示**

三個前端入口共用同一套認證、後端服務與資料來源。

**畫面提示**

顯示商城、營位預約與營運後台，往下連接認證層、Spring Boot 與 PostgreSQL 的架構圖。

**後端流程**

使用者操作前端  
→ 前端取得 Firebase 身分憑證  
→ Controller 接收並驗證請求  
→ Service 執行業務規則  
→ Repository 存取 PostgreSQL  
→ 回傳固定資料格式供前端呈現

**完整講稿**

Yuruicamp 包含購物商城、營位預約與營運後台三個前端入口，但它們共用同一套 Spring Boot 後端。前端提出請求時會攜帶 Firebase 身分憑證，後端先確認使用者身分，再由 Controller 接收資料，交給 Service 執行狀態、資格與交易規則，最後透過 Repository 存取 PostgreSQL。前端主要負責互動與呈現，真正會改變訂單、預約、庫存與權限的判斷都由後端統一處理。

**轉場**

有了共用架構後，先從其他交易流程都會依賴的商品與庫存資料開始。

**建議時間：約 70 秒**

---

## 2. 商品與庫存

**本段目的**

說明商品資料如何分層，以及多張資料表如何在一次交易中保持一致。

**核心提示**

商品不是單一資料表，而是主檔、規格、圖片與各庫位庫存的組合。

**畫面提示**

顯示商品主檔、商品規格、庫位庫存與交易提交的四段式流程圖。

**後端流程**

前端送出商品資料  
→ 鎖定並驗證商品  
→ 同步主檔、圖片與規格  
→ 驗證庫位及庫存數量  
→ 依固定順序鎖定庫存  
→ 更新指定庫位數量  
→ 整筆交易提交或回滾

**完整講稿**

商品與庫存管理負責商品主檔、圖片、SKU 規格及各門市庫存。更新時，後端先鎖定商品並驗證 SKU、上下架狀態與有效規格。請求中沒有出現的既有規格不會直接刪除，而是改為停用，避免歷史訂單失去參照。接著後端只更新本次指定的庫位，未傳入的庫存維持原值。商品、規格、圖片與庫存都放在同一個交易中，任何一步失敗就會一起回滾。

**轉場**

商品資料建立後，下一個問題是如何安全記錄並執行每一次庫存變化。

**建議時間：約 85 秒**

---

## 3. 庫存異動紀錄

**本段目的**

說明後端如何處理庫存調撥、保留量與併發更新。

**核心提示**

庫存異動必須先鎖定資源，再驗證真正可使用的數量。

**畫面提示**

顯示草稿、鎖定、保留量檢查、庫存更新、過帳與稽核的水平流程。

**後端流程**

建立異動草稿  
→ 鎖定異動單  
→ 依規格與庫位固定排序鎖定庫存  
→ 檢查來源數量與有效保留量  
→ 同一交易完成來源扣除與目的增加  
→ 異動單過帳  
→ 保存操作者與異動歷程

**完整講稿**

庫存異動紀錄讓每一次庫存變化都可以追蹤。異動單會先以草稿保存，通過檢查後才能過帳。租借庫存互轉時，Service 會先鎖定異動單，再依商品規格與庫位的固定順序鎖定庫存，降低並行操作發生死鎖的風險。系統還會扣除已被訂單或租借預約保留的數量，確認真正可用庫存足夠，才在同一交易內完成來源扣除、目的增加與異動紀錄。

**轉場**

庫存可安全異動後，就能進入會實際消耗商品與資源的訂單履約流程。

**建議時間：約 75 秒**

---

## 4. 訂單管理

**本段目的**

說明訂單不能任意改狀態，而要由後端狀態機控制履約與取消。

**核心提示**

每個管理動作都必須符合目前的訂單、付款與退款狀態。

**畫面提示**

顯示讀取訂單、鎖定狀態、驗證轉換、履約或取消、同步付款與寫入歷程的流程圖。

**後端流程**

管理員提出操作  
→ 鎖定目前訂單  
→ 驗證訂單與付款狀態  
→ 執行出貨、完成或取消  
→ 同步付款、庫存保留與優惠券  
→ 寫入操作者、時間與原因  
→ 回傳最新訂單內容

**完整講稿**

訂單管理提供查詢、詳情、出貨、完成與取消，但管理員不能直接指定任意狀態。正常履約由未出貨進入已出貨，再進入已完成；取消也只能在後端允許的狀態執行。操作時，Service 會先鎖定訂單，檢查履約、付款與退款狀態，再處理對應動作。若取消已付款訂單，會先完成退款，成功後才同步訂單、庫存保留與優惠券，並保存管理員操作歷程。

**轉場**

訂單除了商品與付款，也可能套用折扣，因此下一段說明優惠券如何維持完整生命週期。

**建議時間：約 80 秒**

---

## 5. 折扣管理

**本段目的**

說明優惠券主檔、會員領取紀錄與訂單快照如何分工。

**核心提示**

優惠券不是一個折扣欄位，而是一套包含名額、資格、狀態與歷史的生命週期。

**畫面提示**

顯示優惠券主檔、領取紀錄、訂單快照，以及建立、領取、結帳、核銷的流程。

**後端流程**

建立優惠活動  
→ 驗證規則、效期與發行量  
→ 會員領取時原子配置名額  
→ 結帳時建立折扣快照  
→ 付款成功後才正式核銷  
→ 已有領取紀錄的活動只能停用

**完整講稿**

優惠券分成三層：主檔保存折扣規則、效期與名額；會員領取紀錄保存領取者與使用狀態；訂單則保存結帳當下的優惠快照。多人同時領券時，名額由資料庫原子配置，避免最後一張被重複領取。優惠券套用到訂單時只先建立快照，付款成功後才由已領取轉成已核銷。管理員修改活動時，發行量不能低於已領數；已有領取紀錄也不能刪除，只能停用。

**轉場**

優惠資格與訂單都會連結會員，因此接著介紹後台如何管理會員目前資料與歷史交易。

**建議時間：約 80 秒**

---

## 6. 客戶管理

**本段目的**

說明會員目前資料、後台查詢模型與訂單歷史快照的界線。

**核心提示**

會員資料可以更新，但已成立交易的內容不能跟著改變。

**畫面提示**

顯示會員讀模型、停權即時生效與地址快照邊界的三段式畫面。

**後端流程**

後台彙整會員資料  
→ 組合基本資料、消費、標籤與偏好  
→ 管理員可更新會員或執行停權  
→ 後端鎖定並更新目前狀態  
→ 會員再次請求時重新查詢狀態  
→ 非啟用狀態立即拒絕

**完整講稿**

客戶管理會把會員基本資料、消費摘要、標籤、偏好與預設地址組成後台需要的讀取模型。資料同時區分目前狀態與交易快照，例如管理員更新會員地址，只會影響會員現在的資料，不會回寫既有訂單的收件內容。停權時，後端會鎖定會員並更新狀態；會員下一次提出請求時，Firebase 雖然能確認身分，後端仍會重新查詢資料庫，只要不是啟用狀態就立即拒絕。

**轉場**

會員完成購買後可能留下評論，下一段說明評論如何連結真實交易並保持歷史內容。

**建議時間：約 70 秒**

---

## 7. 評論管理

**本段目的**

說明評論如何驗證購買資格、正確分頁並維持關聯資料完整性。

**核心提示**

評論可信度與歷史內容都由後端交易資料決定，而不是相信前端宣告。

**畫面提示**

顯示購買資格、兩階段分頁，以及刪除評論與照片的三段式流程。

**後端流程**

前端送出篩選與分頁條件  
→ 後端驗證評分、日期與排序  
→ 先查詢當頁評論識別資料  
→ 批次取得評論、交易快照與照片  
→ 依原順序組成回傳資料  
→ 刪除時一併清除關聯照片

**完整講稿**

評論管理提供搜尋、評分與日期篩選、詳情及整則刪除。後端會透過訂單明細確認評論者真的購買過商品，而不是接受前端自行標記。查詢時先取得當頁評論識別資料，再批次載入評論、商品快照與照片，避免一對多關聯造成分頁筆數重複。評論保存購買當下的商品名稱、SKU 與購買者資料；刪除評論時，資料庫會同步清除關聯照片，維持完整性。

**轉場**

商城流程說明完成後，接著進入營位預約，先從後台掌握每日供需的排程面板開始。

**建議時間：約 65 秒**

---

## 8. 預約排程面板

**本段目的**

說明每日營位容量如何轉換成前後台一致的月曆狀態。

**核心提示**

後台月曆與前台可預約檢查必須共用同一套可用性來源。

**畫面提示**

顯示 available、low、full、closed、out_of_window 五種狀態，以及每日容量推導流程。

**後端流程**

管理員選擇營區與月份  
→ 讀取各營位每日容量與占用量  
→ 套用停售、公休與特殊營業日  
→ 比對預約視窗及低量門檻  
→ 推導每日狀態  
→ 點選日期後載入當晚實際預約

**完整講稿**

預約排程面板把每日容量整理成可預約、低量、已滿、公休與超出預約期間五種狀態。後端先彙總各營位每天的容量、已訂、停售與剩餘量，再套用公休、特殊營業日、預約視窗與低量門檻。這套資料來源也提供前台可預約檢查，因此後台月曆與使用者實際能否預約會保持一致。管理員點選日期後，還能查看當晚實際占用的顧客、營位與數量。

**轉場**

排程面板呈現整體供需，下一段則進入單筆預約、付款與租借資源的生命週期。

**建議時間：約 85 秒**

---

## 9. 預約／租借管理

**本段目的**

說明預約狀態、付款狀態與租借庫存保留如何同步前進。

**核心提示**

預約完成或取消時，不能只改主檔狀態，還要同步處理相關資源。

**畫面提示**

顯示 pending、confirmed、completed、cancelled 狀態，以及租借保留量的處理流程。

**後端流程**

建立預約與交易快照  
→ 驗證可信付款結果  
→ 預約進入確認狀態  
→ 建立營位與租借資源保留  
→ 完成時將保留轉為已履約  
→ 取消時先退款再釋放資源  
→ 寫入完整狀態歷程

**完整講稿**

預約詳情由預約主檔、營位快照、租借快照與狀態歷程組成。狀態正常由待處理、已確認進入已完成，取消只能在允許的階段執行。只有付款流程確認成功的預約才能進入已確認。完成預約時，後端會鎖定資料、驗證付款與狀態，再把租借保留量轉為已履約；取消已付款預約時，則先完成退款，成功後才釋放營位與租借保留，並保存管理員操作歷程。

**轉場**

商城與預約交易都累積了營運資料，接著說明後端如何將這些明細轉成一致的分析指標。

**建議時間：約 85 秒**

---

## 10. 分析報表

**本段目的**

說明指標計算為什麼集中在後端，而不是由前端自行統計。

**核心提示**

前端負責畫圖，後端負責定義與聚合營運指標。

**畫面提示**

顯示營收趨勢、分類占比、商品排行、預約收入與取消率等分析圖表。

**後端流程**

管理員選擇日期區間  
→ 後端驗證查詢範圍  
→ Service 定義指標口徑  
→ Repository 在 PostgreSQL 聚合資料  
→ 組成指標、趨勢、排行與占比  
→ 前端轉換成卡片與圖表

**完整講稿**

分析報表分成裝備商城與預約租借兩個區塊，提供營收趨勢、訂單、退款、熱銷商品、預約收入與取消率。管理員選擇日期後，Service 先驗證範圍並定義各項指標，再由 Repository 直接在 PostgreSQL 完成聚合，回傳固定的指標、趨勢、排行與類別占比。前端只需要轉換成卡片和圖表，不必下載大量明細重新計算，也能確保不同畫面使用相同口徑。

**轉場**

最後，所有分析與管理操作都必須受授權控制，因此進入權限管理。

**建議時間：約 70 秒**

---

## 11. 權限管理

**本段目的**

說明登入身分、角色基準、個人例外與後端即時授權如何共同運作。

**核心提示**

前端可以隱藏功能，但真正的權限執行點必須在後端。

**畫面提示**

顯示 Firebase 身分驗證、管理員白名單、角色與個人權限，以及後端放行判斷。

**後端流程**

Firebase 確認登入身分  
→ 後端檢查管理員白名單與啟用狀態  
→ 載入角色基準權限  
→ 套用個人允許與拒絕設定  
→ 每次請求重新計算有效權限  
→ 安全規則避免管理能力歸零

**完整講稿**

權限管理分成身分與授權兩層。Firebase 先確認登入者是誰，後端再檢查 Email 是否在管理員白名單、帳號是否啟用。系統先由角色提供基本權限，再套用個人的允許與拒絕設定，計算實際可用功能。每次後台請求都會由後端重新判斷，因此即使前端仍保留舊畫面，無權限操作仍會被拒絕。更新時也會防止自我停權，並確保至少保留一名可管理權限的啟用管理員。

**轉場**

無；權限管理講完即結束報告，不另外加入總結頁。

**建議時間：約 85 秒**
