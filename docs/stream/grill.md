## 分析報表

1. 目的：將交易資料轉換成營運資訊
    裝備商城：營收趨勢、訂單、退款、熱銷商品
    預約／租借：預約收入、取消率、租借占比
    支援日期區間篩選與前後期比較
    前端只負責呈現，統計口徑由後端統一處理

2. 後端流程
    前端選擇日期區間
            ↓
    GET /api/admin/analytics/shop-summary
            ↓
    Controller：驗證身分與 analytics.view 權限
            ↓
    Service：驗證日期、定義 KPI、組合結果
            ↓
    Repository：透過 JDBC 在 PostgreSQL 聚合資料
            ↓
    DTO：回傳 KPI、趨勢、排行與類別占比
            ↓
    前端轉換成卡片與圖表

3. 口條
    這是 Admin 的分析報表，主要分成裝備商城與預約租借兩個區塊。管理者可以依日期區間查看營收趨勢、訂單、退款、熱銷商品，以及預約收入和取消率等資訊。  
    使用者選擇日期後，前端會呼叫API。Controller 會先驗證登入身分以及 analytics 權限；沒有權限就回傳 403。  
    通過權限後，Service 會驗證日期範圍、定義各項 KPI，接著由 Repository 透過 JDBC 向 PostgreSQL 查詢。完成營收、每日趨勢、商品排行與類別占比等聚合。  
    最後，固定 DTO 回傳，前端只需要轉換成卡片和圖表。這樣由後端集中彙總，可以減少明細資料的傳輸量，也能確保不同頁面使用相同的指標口徑。預約分析則沿用相同的分層流程。


## 訂單管理

1. 目的：集中管理訂單查詢與履約流程
    查詢：關鍵字、日期、付款與訂單狀態篩選
    詳情：顧客、收件、商品、金額與內部備註
    履約：出貨、完成、取消
    稽核：保留管理員操作與狀態歷程

2. 取消訂單的後端流程
    前端提出取消請求
            ↓
    Controller：驗證 orders.edit 權限
            ↓
    Service：鎖定訂單並檢查狀態
            ↓
    已付款線上訂單 → Payment Gateway 退款
    未付款訂單     → 直接進入取消流程
            ↓
    同一交易更新訂單、庫存保留與優惠券
            ↓
    寫入管理員操作歷程
            ↓
    回傳最新訂單 DTO
    
3. 口條
訂單管理主要提供訂單查詢、詳情檢視、履約操作與歷程追蹤。管理員可以依日期、付款方式及訂單狀態篩選資料，並執行出貨、完成或取消。  
訂單狀態不能任意修改，正常流程是從未出貨、已出貨到已完成；只有未出貨訂單可以取消。Controller 也透過 RBAC 分離查詢、修改訂單的權限，
如果取消已付款訂單。Service 會先鎖定訂單，檢查目前的履約、付款與退款狀態。符合條件後，先透過 Payment Gateway 執行退款；退款成功才更新本地資料。 
接著，由 Spring Boot 後端統一維護交易中更新訂單、釋放庫存保留、處理優惠券並寫入管理員操作歷程等資料。


## 庫存異動紀錄

1. 目的：讓每一次庫存變化都可管理、可追溯
    查詢：依期間、人員、領域與異動類型篩選
    明細：庫位、商品規格、數量、原因與異動性質
    稽核：保存操作者、異動時間及單據狀態
    權限：查看與異動操作分離

2. 租借庫存互轉流程
    前端建立異動草稿與明細
                ↓
    Controller：驗證 movement.edit 權限
                ↓
    Service：鎖定異動單並檢查草稿狀態
                ↓
    依「商品規格＋庫位」固定順序鎖定庫存
                ↓
    檢查來源庫存與有效預約保留量
                ↓
    同一交易：來源扣除＋目的增加
                ↓
    異動單標記為已過帳
                ↓
    回傳最新異動 DTO

3. 口條
    庫存異動紀錄用來管理及追蹤每一次庫存變化。可以依日期、人員與異動類型查詢，並查看庫位、商品規格、數量、原因及操作者等資料。權限也分為查詢與編輯兩個權限。
    異動單會先建立為草稿，加入明細並通過後端檢查後，才能過帳或作廢。系統中需要區分兩種語意：商城的 update 是商品庫存修改後的稽核紀錄，過帳只會定稿；租借的 transfer 則代表營地之間的實際庫存調撥。  
    以租借互轉為例，Spring Boot Service 會先鎖定異動單，再透過 JDBC 依商品規格與庫位的固定順序鎖定 PostgreSQL 庫存。系統會確認來源扣除後，不會低於有效預約的保留數量，接著在同一交易中完成來源扣除、目的增加及過帳。


## 商品與庫存

1. 目的：集中管理商品資料、規格與各門市庫存
    裝備主檔
    名稱、分類、品牌、描述、圖片
            ↓
    商城商品
    上架／下架狀態
            ↓
    商品規格
    SKU、顏色、尺寸、價格、狀態
            ↓
    庫位庫存
    各規格在不同門市的現有數量

2. 商品與庫存更新流程
    前端送出商品更新資料
            ↓
    Controller：驗證 products.edit 權限
            ↓
    Service：鎖定商品並驗證資料
            ↓
    同步商品主檔、圖片與規格
            ↓
    驗證指定庫位與庫存數量
            ↓
    依「規格＋庫位」順序鎖定庫存
            ↓
    更新指定庫位的 on-hand 數量
            ↓
    交易提交並回傳完整商品 DTO

3. 口條
    商品與庫存管理，主要負責商城商品、規格、圖片與各門市庫存。資料結構分成四層：最上層是裝備主檔，保存名稱、分類、品牌與圖片；接著是商城商品的上下架狀態；每個商品可以有多個 SKU 規格；每個規格再分別記錄各庫位的庫存。
    以更新商品為例，Spring Boot Service 會先鎖定商品，驗證 SKU 不可重複，而且上架商品至少要有一個有效規格。新規格由後端產生 ID；請求中缺少的既有規格不會直接刪除，而是改成停用，以保留訂單與歷史資料的關聯。
    商品主檔、規格與圖片透過 JPA 同步；庫存則透過 JDBC 驗證並鎖定指定的商城庫位，再寫入 PostgreSQL。沒有傳入的庫位維持原資料。整個流程位於同一交易中，任何一步失敗都會回滾。透過分層模型、狀態管理與原子交易，系統可以安全維護商品與庫存，同時保留完整的歷史關聯。


## 客戶管理

1. 目的：整合會員目前資料與交易摘要
    管理員提出停權操作
            ↓
    Service 鎖定會員資料
            ↓
    檢查目前會員狀態
            ↓
    active → suspended
            ↓
    會員再次攜帶 Firebase Token 請求
            ↓
    Firebase 驗證 Token 身分
            ↓
    後端重新查詢 PostgreSQL 會員狀態
            ↓
    非 active → 拒絕建立登入身分

2. 口條
客戶管理，整合四類資料：會員基本資料、標籤與偏好、預設收件地址。
客戶列表使用後端把會員主檔與相關的7張資料表組成 DTO 顯示。
資料區分目前狀態與歷史快照。例如管理員修改會員的預設地址時，只會更新會員目前的地址，不會回寫既有訂單的收件資料，確保交易當下的紀錄不被改變。
以停權為例，Spring Boot Service 會透過 JPA 鎖定會員，確認不是已刪除帳號後，再把狀態由 active 改為 suspended。會員下次提出請求時，Firebase 先驗證 Token 身分，但後端仍會重新查詢 PostgreSQL 中的會員狀態。只要不是 active，即使 Token 尚未過期也不會建立登入身分。  
因此 Firebase 負責確認使用者是誰，後端會員狀態則決定這個人目前能否使用系統，讓停權可以立即生效，同時保留完整的會員與交易歷史。


## 折扣管理

1. 有一套完整生命週期
        優惠券主檔
        代碼、折扣、門檻、效期、名額、類型
                ↓
        會員領券紀錄
        領取者與 claimed／consumed／revoked／expired 狀態
                ↓
        訂單優惠快照
        套用當下的優惠內容與實際折扣金額
    使用流程:
        claimed
            ↓ 套用至結帳訂單
        建立優惠快照，但尚未核銷
            ↓ 付款成功
        consumed

2. 更新已發行優惠券
    管理員送出更新資料
            ↓
    Service 鎖定優惠券
            ↓
    驗證折扣、效期與適用類型
            ↓
    確認發行數量 ≥ 已領取數量
            ↓
    更新優惠券或將其停用
            ↓
    保留會員領券與訂單快照

3. 口條
優惠券分成三層資料：第一層是優惠券主檔，保存折扣方式、最低消費、效期、名額與適用類型；第二層是會員領券紀錄；第三層則是訂單套用優惠時建立的交易快照。  
優惠券包含一般活動券、生日券與首購券。後端會依優惠券狀態、有效期間、剩餘名額、最低消費，以及會員生日或首購資格判斷是否可以領取及使用。多人同時領券時，名額由 PostgreSQL 原子配置，避免最後一張券被重複領取。
優惠券被套用到結帳訂單時，只會先建立優惠快照並計算折扣，不會立即核銷；等付款成功後，領券狀態才會由 claimed 轉為 consumed，避免未完成付款就浪費優惠券。  
在 Admin 更新已發行優惠券時，會先鎖定資料，驗證折扣、效期與名額。發行數不能低於已領數；如果已有領券紀錄，也不能直接刪除，只能停用，藉此保留會員領券與訂單歷史。  
因此優惠券是一項包含名額、會員資格、領取狀態與交易快照的完整生命週期，後端必須同時維持規則一致性與歷史可追溯性。

## 預約排程面板

1. 目的：以月曆掌握每日營位供需
    狀態	        意義
    available	    尚有足夠營位
    low	            剩餘量低於系統門檻
    full	        已無剩餘營位
    closed	        營區公休
    out_of_window	不在可預約期間

    營運設定：
        公休：指定日期區間或每週固定星期
        特殊節日：仍可預約，但套用特殊節日價格
        可切換營區、單一營位或全部營位檢視

2. 後端流程
        前端選擇營區、營位與月份
                    ↓
        Admin Availability API
                    ↓
        PostgreSQL 共用可用性函式
                    ↓
        計算容量、已訂、停售與剩餘量
                    ↓
        套用公休、特殊節日與預約視窗
                    ↓
        Service 組成每日狀態 DTO
                ↓
    前端繪製月曆

    * 點選日期後：
        單晚占用預約 API
                ↓
        查詢該晚實際占用的預約
                ↓
        回傳顧客、營位、數量及住宿區間

3. 口條
主要讓管理員透過月曆掌握每日營位供需。後端依供需結果標示為可預約、低庫存、已滿、公休或超出預約期間。  
選擇月份後，Spring Boot Service 驗證日期與營區範圍後，透過 JDBC 呼叫 PostgreSQL 的函式，取得各營位每天的容量、已訂、停售與剩餘數量，再由 Service 聚合並套用預約政策。
這套計算與前台的可預約檢查共用資料來源，因此後台看到的剩餘量會和使用者實際能否預約保持一致。  
月曆整合公休與特殊節日。公休代表當日不可預約；特殊節日仍可預約，但結帳時會使用特殊節日價格。點選某一天後，系統會再呼叫單晚占用預約 API，顯示實際占用的顧客、營位與數量。
此外，管理員調降營位總數時，後端會先比較未來占用峰值；若新容量不足，就回傳 409，避免既有預約形成超訂。整體設計以單一可用性來源，維持前後台數據一致。


## 預約/租借管理

1. 目的：集中管理預約、付款與租借資源
        預約主檔
        營區、住宿日期、聯絡人、付款與預約狀態
                +
        營位快照
        類型、數量、平日／假日價格
                +
        租借快照
        SKU、規格、數量、價格與折扣
                +
        狀態歷程
        操作時間、管理員與備註

    狀態流程：
        pending → confirmed → completed
        └──────────────→ cancelled
                    confirmed ─→ cancelled

2. 完成與取消流程
    完成: 
        鎖定預約
        ↓
        驗證 confirmed＋paid
        ↓
        更新為 completed
        ↓
        租借保留轉為已履約
        ↓
        寫入操作歷程

    取消已付款預約: 
        鎖定預約並驗證狀態
                ↓
        Payment Gateway 全額退款
                ↓ 成功後
        更新為 cancelled＋refunded
                ↓
        釋放營位占用與租借保留
                ↓
        寫入操作歷程

3. 口條
    預約詳情由四部分組成：預約主檔、營位快照、租借快照及狀態歷程。營位類型、租借 SKU、規格、平假日價格與折扣，預約紀錄都使用交易快照。
    預約採用狀態機管理，正常流程是從 pending、confirmed 到 completed。只有可信付款流程已標記為 paid 的預約，管理員才能確認。完成預約時，Spring Boot Service 會先鎖定資料並驗證狀態，再更新為 completed，將租借庫存保留轉為已履約，最後寫入操作歷程。  
    如果取消已付款的 pending 或 confirmed 預約，系統會先透過 Payment Gateway 執行全額退款。只有退款成功後，才會更新為 cancelled 與 refunded、釋放營位占用及租借保留，並保存歷程。退款失敗則不修改本地狀態。目前本機以 Stub 驗證流程，正式支付商退款 HTTP 尚待接通。


## 權限管理

1. 登入與授權：
    Firebase 驗證身分
            ↓
    確認 Email 在管理員白名單
            ↓
    檢查帳號啟用狀態及 UID 綁定
            ↓
    載入實際可用權限
            ↓
    後台 API 依權限決定是否放行

2. 安全更新權限
    管理員送出權限設定
            ↓
    鎖定啟用中的管理員集合
            ↓
    鎖定目標管理員帳號
            ↓
    執行管理者安全檢查
            ↓
    保存個人權限設定
            ↓
    下一次 API 請求重新載入權限

    安全規則：
        不能停用自己的帳號
        不能移除自己的權限管理能力
        至少保留一名啟用中的權限管理者
        至少保留一個啟用中的 Admin 角色帳號
        並行修改時仍能避免管理權限歸零

3. 口條
    系統採用角色加上個人設定的方式。角色先提供基本職責範圍，再透過個人權限處理特定人員的例外，最後由後端計算該管理員實際可以使用的功能。  
    登入時，Firebase Authentication 先確認使用者身分。後端接著檢查 Email 是否存在於管理員白名單、帳號是否啟用，以及 Firebase UID 是否與帳號正確綁定。全部通過後，才會載入實際權限。  
    權限的最終執行點在 Spring Boot Security。每次後台 API 請求都會重新讀取管理員帳號與最新權限，再決定是否放行。因此即使前端仍保留舊畫面，已被移除權限的操作仍會由後端拒絕。  
    更新權限時，後端也會阻止管理員停用自己、移除自己的管理能力，並確保至少保留一名權限管理者及一個啟用中的 Admin 角色帳號。  
    因此，Firebase 負責確認管理員是誰，角色提供基本職責，個人設定處理例外；最終由後端即時授權，並透過安全規則避免系統失去管理控制權。
